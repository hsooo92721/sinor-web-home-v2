# 시럽인연 개발 전달서


## 코웨이 라이프솔루션 제휴

2026-11-11 · 기준 저장소 `sinor-web-home-v2`

### 작업 범위

- 코라솔 랜딩 URL 한 개를 추가합니다. 기존 페이지, URL, 공통 푸터 적용 범위는 유지합니다. 전체 페이지 공통 푸터 적용은 별도 작업으로 진행합니다.
- 기존 상담 접수·Slack·시럽인연 어드민에는 코웨이 유입경로에 필요한 변경만 반영합니다.

### 랜딩페이지

- 예정 URL은 `https://web.sinor.co.kr/silovematch/coway-life-solution/`입니다.
- 코웨이 라이프솔루션 제휴 안내 페이지의 **상담 및 예약 바로가기**를 위 URL로 연결합니다.
- `silovematch/coway-life-solution/index.html`과 첨부 캡처를 화면 기준으로 사용합니다. 상단에는 가입비 30만 원 할인 혜택을 안내하고, **제휴 혜택 상담 신청** 버튼은 같은 페이지의 폼으로 이동합니다.
- 운영 중인 `https://web.sinor.co.kr/silovematch-consult/`의 상담폼 컴포넌트와 신청 처리 로직을 재사용합니다. 입력 항목·필수값·선택 모달·동의 문구·로그인 정보 처리·완료 화면은 운영 폼과 동일하게 적용합니다.
- 첨부 HTML은 디자인 및 입력 동작 확인용입니다. 현재 `renderForm(..., { preview: true })`로 구성되어 있어 개발 시 운영 폼의 접수 흐름을 연결해야 합니다. 제휴 혜택 대상 확인과 할인 적용은 운영 정책을 따릅니다.

### 신청 저장과 유입경로

- 코웨이 랜딩에서 완료된 **상담 신청 건**에 유입경로 **코웨이 라이프솔루션**을 저장합니다. 기존 상담 저장 및 준회원 연결 흐름에 추가합니다.
- 경로 코드는 기존 서버의 유입경로 체계에 맞춰 정합니다. 페이지 경로만 보고 어드민에서 추측하는 대신, 접수 시 서버가 신청 기록에 경로를 남겨 Slack과 어드민이 같은 값을 사용하도록 합니다.
- 회원에게 기존 유입경로가 있으면 유지하면서 코웨이 경로를 추가하고, 같은 경로는 중복 표시하지 않습니다. 일반 상담 신청과 코웨이 상담 신청이 모두 있으면 신청 원본별로 각각의 유입경로가 표시되어야 합니다.

### Slack 접수 알림

- 기존 시럽인연 상담에 연결된 **서버 측 웹훅·채널·메시지 형식**을 재사용합니다. 웹훅 URL은 현재 운영 설정에서 참조합니다.
- 코웨이 신청 건에만 기존 메시지 항목 **유입경로 · 코웨이 라이프솔루션**을 추가합니다.
- 기존 **신청 원본 보기** 버튼은 지금과 같은 방식으로 해당 신청 건의 원본 모달을 엽니다. 링크에는 기존 식별자·권한 확인 방식을 그대로 적용합니다.

### 시럽인연 어드민

- `silovematch/coway-life-solution/admin-preview.html?view=original`을 열면 신청 원본 모달 시안을 볼 수 있습니다. 모달을 닫으면 준회원 상세 시안이 보입니다.
- **신청 원본 모달**의 제목 위에 있는 보라색 **시럽인연 상담** 태그 옆에 같은 형태의 **코웨이 라이프솔루션** 태그를 추가합니다. 포인트 컬러는 `#0074FF`입니다. 선택한 신청 기록에 코웨이 유입경로가 있을 때만 표시합니다.
- **준회원 상세**에서는 상단 **유입경로**에 코웨이 라이프솔루션을 표시합니다. 이름 옆에는 태그를 추가하지 않습니다.
- 첨부 어드민 HTML은 예시 데이터로 만든 시안입니다. 운영 어드민의 기존 상세·모달 컴포넌트에 위 표시만 반영합니다.

### 코라솔 랜딩 푸터

- 첨부한 최신 푸터 디자인을 코라솔 랜딩에 적용합니다. PC에서는 스토어 뱃지를 우측 상단에 배치하고, 모바일에서는 사업자정보 아래에 배치합니다. 문의 번호는 **02-508-5670**입니다.
- 랜딩 푸터의 메뉴와 스토어 뱃지는 운영 주소 전체를 포함한 HTTPS 링크를 사용합니다. 채용·여행약관·여행특별약관은 기존 공식 사이트 메뉴에서 확인한 주소이며, 배포 전 정상 열림을 확인해 주세요.
- 아동안전표준 정책의 운영 주소는 미확인 상태입니다. 시안에는 메뉴명만 표시했습니다. 배포 전 운영팀에서 현재 주소를 받아 전체 HTTPS URL을 연결해 주세요.

### 적용 확인

1. 코웨이 안내 페이지 버튼에서 예정 랜딩 주소가 열리고, PC·모바일에서 상담폼까지 이동하는지 확인합니다.
2. 코웨이 신청을 테스트하면 기존 방식으로 접수되고, Slack 알림 한 건에 코웨이 유입경로가 표시되는지 확인합니다.
3. Slack에서 해당 신청 원본을 열면 파란 태그가 보이고, 닫은 뒤 준회원 상세의 유입경로에만 코웨이가 추가되는지 확인합니다.
4. 일반 상담과 기존 유입경로, 기존 Slack 링크 동작을 함께 확인합니다.
5. 코웨이 랜딩의 푸터 메뉴와 스토어 링크 네 개를 확인합니다. 기존 페이지의 주소와 푸터는 이번 배포 범위에서 제외합니다.

### 첨부 소스 적용 방법

ZIP에는 코라솔 랜딩 전용 소스와 전달자료를 담았습니다. 시안은 기존 저장소의 `cms/` 폼 렌더러와 `assets/vendor/` 폰트에 의존합니다. 기준 저장소 루트에서 HTTP 서버를 실행한 뒤 `/silovematch/coway-life-solution/`로 접속하면 됩니다. 운영 배포 시 실제 상담폼을 연결하고 시안용 `noindex` 설정은 운영 정책에 맞춰 결정합니다. 첨부 캡처는 디자인 확인용이며 최종 링크는 HTML을 기준으로 확인합니다.


### 배포 후 검증 실행 프롬프트

아래 프롬프트를 개발 에이전트에 붙여넣어 실행합니다. 배포 완료 후 운영 환경의 테스트 신청과 Slack·어드민 접근은 담당자가 승인한 계정과 테스트 데이터로 진행합니다.

> 코웨이 라이프솔루션 제휴 랜딩의 배포가 완료되면 아래 검증을 실제로 실행해 주세요. 코드 검토만으로 완료 처리하지 말고, 하나의 테스트 신청을 제출해 접수부터 Slack, 어드민까지 추적해 주세요.
>
> 1. 코웨이 제휴 안내 페이지의 **상담 및 예약 바로가기**를 눌러 배포된 `https://web.sinor.co.kr/silovematch/coway-life-solution/`이 열리는지 확인합니다. 링크 수정 권한이 없다면 담당자에게 확인을 요청하고 랜딩 검증은 계속합니다.
> 2. 상담폼에 승인된 테스트 이름과 연락처를 입력하고, 문의 내용에 **[배포검증] 코웨이 라이프솔루션**과 실행 시각을 남깁니다. 실제 고객 정보는 사용하지 않습니다. 테스트 신청에 고객 연락이나 문자 발송이 이어지지 않도록 운영팀과 사전에 조율합니다.
> 3. 신청을 **한 번** 제출하고 완료 화면, 접수 시각, 신청 ID를 확인합니다. 응답이 불명확하면 기존 접수부터 조회한 뒤 재시도 여부를 판단합니다.
> 4. 기존 Slack 채널에서 같은 시각과 테스트 표시가 있는 접수 메시지를 찾습니다. 동일 신청의 알림이 한 건인지, **유입경로 · 코웨이 라이프솔루션**이 표시되는지 확인합니다.
> 5. Slack 메시지의 **신청 원본 보기**를 열어 같은 신청인지 확인합니다. 원본 모달에서 **시럽인연 상담** 태그 옆에 파란색 **코웨이 라이프솔루션** 태그가 표시되어야 합니다.
> 6. 모달을 닫고 준회원 상세를 확인합니다. 코웨이는 **유입경로**에 표시되고, 기존 경로가 있는 회원이면 기존 값도 함께 보여야 합니다. 이름 옆에는 코웨이 태그가 없어야 합니다. 기존 일반 상담 기록에도 코웨이 태그가 붙지 않았는지 확인합니다.
> 7. 결과를 **랜딩 이동 / 접수 / Slack / 신청 원본 / 준회원 상세**별로 통과·실패·확인 불가로 정리합니다. 배포 URL, 실행 시각, 신청 ID, 권한이 있는 내부 확인 링크 또는 개인정보를 가린 캡처를 남깁니다. 접근 권한이 없어 확인하지 못한 단계는 필요한 담당자나 권한을 적습니다. 테스트 기록은 운영팀이 정한 방식으로 정리합니다.

## 공통 상단 헤더

### 이벤트 구현본

- 이벤트 목록 및 상세는 `silovematch/shared/header.js`와 `header.css`를 공유합니다. `mountSilovematchHeader()`에 헤더 요소를 넘기면 동일한 로고와 메뉴가 표시됩니다.
- PC는 좌측 로고와 우측 가로 메뉴, 모바일은 햄버거 메뉴와 세로 메뉴입니다. 모바일 메뉴는 링크 선택, 바깥 클릭, Escape로 닫힙니다.
- 이벤트 본문 미리보기에는 헤더를 띄우지 않습니다.

### 운영 서비스 적용 요청

1. 운영 시럽인연 메인 https://web.sinor.co.kr/silovematch/ 및 상담 신청 페이지 등 하위 페이지의 공통 레이아웃에 동일한 헤더를 연결합니다. 현재 로고만 표시되는 헤더는 원본 컴포넌트에서 교체하고 페이지별 헤더가 중복되지 않도록 합니다.
2. `silovematch-consult-screen_pageHeader____C6e`와 `silovematch-consult-screen_headerInner__WG8_5`는 빌드 결과에서 원본을 찾기 위한 참고 클래스입니다. 운영 프로젝트의 원본 컴포넌트와 스타일에서 적용합니다.
3. 로고는 `/silovematch/`, 1:1 매칭은 `/silovematch/#programs`, 단체미팅은 `/silovematch/#meetings`, 이벤트는 `/silovematch/events/`, FAQ는 `/silovematch/#faq`로 연결합니다.
4. 메인에서는 같은 문서의 해시 링크를 이용해 새로고침 없이 이동합니다. 하위 페이지에서는 메인 주소와 해시를 함께 사용합니다. 메인 섹션 제목이 가려지지 않도록 `scroll-margin-top`을 헤더 높이에 맞춰 적용합니다.
5. 이벤트 목록·상세에서는 공통 헤더의 이벤트 메뉴 글자색을 #93377F로 표시합니다. 링크에는 aria-current="location"을 설정합니다. 메인 섹션 스크롤에 따른 메뉴 강조는 사용하지 않으며 hover·키보드 focus 스타일을 적용합니다. 기존 메인 콘텐츠, 상담·단체미팅 신청, 공통 푸터, 하단 플로팅 상담 버튼은 유지합니다.
6. PC·모바일에서 로고와 메뉴 이동, 상단 고정, 펼침과 닫힘, 하단 상담 버튼과의 배치를 확인합니다.

운영 레이아웃에서 `mountSilovematchHeader(element, {homeUrl: '/silovematch/', eventsUrl: '/silovematch/events/'})`을 사용하거나 같은 구조를 프레임워크의 공통 컴포넌트로 옮깁니다. 첨부 경로를 기준으로 로고 파일의 정적 경로를 연결합니다. 콘텐츠 너비는 `--silovematch-content-width`로 운영 레이아웃과 맞출 수 있습니다.

## 시놀 홈의 칼럼 연동

시놀 홈의 칼럼 카드는 독자용 칼럼 목록과 같은 데이터에서 공개 글을 발행일 최신순으로 가져옵니다. 카드 개수와 레이아웃은 기존 홈을 기준으로 하고, 대표이미지·카테고리·제목을 표시합니다. 뱃지는 칼럼 목록과 같은 색상 설정과 원형 점을 사용합니다. 카드와 전체보기는 각각 상세와 칼럼 목록으로 연결합니다. 홈 우측 시럽인연 상담 배너는 https://web.sinor.co.kr/silovematch/ 로 연결합니다.

### 운영 서버 연동 필수 사항

GitHub Pages는 정적 호스팅이므로 HTTP 301/302 응답, 실시간 서버 SEO, 페이지 접근 제어 및 영속 DB 저장을 실행할 수 없습니다. GitHub에서는 레지스트리 조회 화면만 동작하며 서버 미연결 시 저장을 차단합니다. 이를 실제 운영 완료로 간주하지 않습니다.

1. 회사 서버에 `/_page-management/state`, `/preview`, `/change`, `/navigation` 계약을 연결하거나 `SINOR_PAGE_MANAGEMENT_API`로 API 경로를 지정합니다. `/preview`와 `/change`는 변경 검증 및 커밋 API이며 URL `/dev/` 미리보기와 별개입니다.
2. 제공한 Python 서버는 로컬 검수용으로만 127.0.0.1에 바인딩합니다. 회사 서비스에 그대로 공개하지 않습니다. 기존 관리자 인증·권한·CSRF 정책을 연결하고 실제 로그인 사용자 ID를 수정자로 기록해야 합니다. 현재 수정자는 로컬 관리자입니다.
3. 실제 라우팅과 301/302는 회사 프레임워크/리버스 프록시에 적용해야 합니다. Python의 트랜잭션·중복·순환·하위 경로 변경 검증을 동일하게 유지합니다. 공개/비공개, 소스 파일 별칭 및 이전 URL에서도 우회 접근을 막습니다.
4. SEO/OG는 회사 SSR 또는 서버 응답에 반영합니다. 본문 CMS가 메타데이터를 갱신하는 경우 우선순위를 회사 페이지 컴포넌트에서도 일치시켜야 합니다.
5. 기존 메뉴를 사용하는 회사 공통 헤더·푸터에는 `/navigation` 결과를 연결합니다. 상대 링크·GA4·앱 딥링크·API 경로가 URL 이동에 영향받지 않는지 운영 환경에서 회귀 검수합니다.
6. `/dev/`는 실제 데이터 API를 사용하되 운영 서버의 관리자 인증으로 보호하고 noindex 처리합니다. 신청·결제 등 외부 효과를 발생시키는 기능의 테스트 정책은 기존 회사 정책에 연결합니다.
7. DB 백업과 복구, 서버 재배포 시 데이터 볼륨 유지, 이력 보존을 적용합니다. GitHub 신규 페이지 등록 동기화는 소스 레지스트리만 변경하고 운영 설정 DB를 덮어쓰지 않습니다.

**ZIP으로 새 페이지 생성·수정 (로컬 기능 구현 완료)**

1. 페이지 추가에서 관리자명·Title·상위 위치·Slug·공통 푸터 사용 여부 등 기본정보를 저장합니다.
2. 해당 페이지의 ‘페이지 디자인’에서 HTML/CSS/JS·이미지·폰트 등을 담은 ZIP을 업로드합니다. 최상위 index.html 또는 그 파일을 가진 단일 폴더 구조를 지원합니다. 코드는 UTF-8, 리소스는 상대 경로를 기준으로 구성합니다.
3. 비공개 상태에서는 /dev/해당경로/로 실제 미리보기를 확인합니다. 공개 체크 후 저장하면 정식 경로로 접근할 수 있습니다.
4. ZIP 다운로드로 업로드 원본을 받아 수정하고 ‘ZIP 교체’로 재업로드합니다. 페이지 ID·주소·관리 설정은 유지합니다. 공개 페이지를 교체할 때는 새 ZIP을 미리보기용으로 두고 기존 공개 버전을 유지하며, 확인 후 저장해야 새 버전이 공개됩니다.

- page_bundle.py / page-management.js / pages-admin.js와 미리보기 서버에 업로드·버전 설치·원본 다운로드·공개/미리보기 분기를 연결했습니다. bundleVersion과 publishedBundleVersion을 분리합니다. 기존 CMS 연결 페이지를 임의 ZIP으로 덮어쓰지 않으며 새 일반 페이지·기존 ZIP 페이지를 대상으로 합니다.
- 원본 ZIP은 server/.pages-data/page-bundles/<pageId>/<version>.zip, 리소스는 page-uploads/<pageId>/<version>/, 표시용 래퍼는 managed-pages/<pageId>/index.html에 보관합니다. 전달/서버 이전 시 현재 페이지 메타데이터와 사용 중인 버전의 원본·리소스·래퍼를 함께 내보내야 합니다. Git에서 제외된 DB/ZIP 저장소가 자동으로 전달된다고 가정하지 않습니다.
- ZIP의 JavaScript는 샌드박스 iframe에서 실행하며 어드민 DOM·세션에 접근하지 못하게 합니다. 상대 리소스와 모듈·JSON·이미지를 로드하고 높이를 부모에 전달합니다. 외부 페이지 링크는 사용자 클릭 시 이동하도록 처리합니다. 서버 코드(Node/PHP 등)가 들어 있는 소스 프로젝트 ZIP을 실행하는 기능이 아니며, React/Next 등은 빌드된 정적 결과물이 필요합니다.
- 현재 회사 API·실제 신청 처리·단체미팅 데이터 연결이 완료된 것은 아닙니다. 인증된 회사 데이터가 필요한 ZIP 페이지는 운영 통합 시 명시적인 API/컴포넌트 또는 검증된 메시지 브리지를 연결해야 합니다. API 키·웹훅 URL을 ZIP이나 브라우저 코드에 넣지 않습니다. 정식 운영 SEO는 샌드박스 래퍼/본문의 검색 노출까지 별도로 검수합니다.
- ZIP 50MB / 압축 해제 100MB / 2,000개 파일 한도, 경로 이탈·심볼릭 링크·암호 ZIP·실행 파일·중복 경로 검사, 버전 충돌 및 설치 실패 시 기존 소스 보존을 적용했습니다. 비공개 페이지의 리소스도 정식 경로로는 열리지 않도록 검사합니다.

**실제 검수와 남은 운영 적용**

- Python 자동 검수 22건 + 드래그 판정 Node 검수 4건 통과. HTTP 301/200/404, 폼 연결, 푸터 소스 검증·버전 충돌, ZIP 설치·교체·다운로드, 비공개 리소스 보호, 공개 버전/미리보기 버전 분리를 포함합니다.
- 브라우저에서 오른쪽 3개 탭, 실제 폼 하위 항목과 실제 폼 렌더링, 커스텀 드롭다운 색상, 푸터 HTML/CSS 편집기의 정리·저장 및 scrollWidth=clientWidth를 확인했습니다. 기존 공통 푸터 디자인은 유지했습니다.
- 별도 QA DB에서 ZIP API 업로드, 원본 다운로드 바이트 일치, 수정 ZIP 교체, 실제 HTML/CSS/이미지/JS 모듈/JSON 실행과 공개 URL 렌더링을 확인했습니다. 자동 파일 선택은 Chrome 확장의 파일 접근 제한으로 완료하지 못해 업로드 API로 이어서 검수했습니다. 회사 운영 브라우저의 실제 파일 선택부터 공개까지는 배포 검수에 포함해 주세요.
- 생성한 ZIP 검수용 페이지는 사용자 DB·소스에서 정리했습니다. 사용자 페이지를 테스트 페이지로 교체하지 않았습니다. 현재는 로컬 구현이며 GitHub 커밋·푸시·운영 배포를 수행하지 않았습니다.

### ZIP 웹페이지 직접 렌더링 및 공통 푸터 (2026-11-25 최신 확정)
- ZIP의 index.html을 해당 URL의 최상위 HTML로 제공한다. iframe 래핑과 높이 연동 방식은 사용하지 않는다. 모달·fixed·sticky는 실제 브라우저 viewport를 기준으로 동작해야 한다.
- ZIP 웹페이지는 공통 푸터를 필수 적용한다. 업로드 HTML의 기존 footer는 제거하고 공통 푸터 HTML/CSS를 같은 문서에 삽입한다. 선택 체크박스는 제거한다.
- 직접 렌더링 시에도 기존 sandbox CSP를 유지하며 관리자 권한·인증 저장소 접근을 허용하지 않는다. 운영에서는 업로드 콘텐츠의 격리된 배포 origin 및 회사 API 연동 정책을 함께 검토한다.
- ZIP에 동봉된 Markdown 개발 전달 문서는 보존한다. 업로드가 문서 요구사항을 자동으로 구현하는 기능은 아니다.

### 혜택 신청 후 설문 및 사진 등록 (2026-11-25)
- 신청 완료 → 설문 참여 → 설문 완료 → 아웃핏코드 사진 등록 순서. 두 혜택 신청자의 미완료 설문은 재방문 시 안내한다.
- 기존 시안 정책은 혜택별 설문당 500P, 최대 1,000P. 서버에서는 회원·혜택·설문 버전별 중복 지급을 트랜잭션으로 차단해야 한다.
- 현재 ZIP은 신청과 포인트 지급을 시뮬레이션한다. 실제 회원 조회·설문 저장·포인트 지급 API는 개발 연동 필요. sandbox에서 localStorage 재방문 저장도 제한되므로 운영 상태는 서버에서 조회해야 한다. 지급 성공 응답 후에만 지급 완료를 표시한다.
- 브라우저에서 신청 완료 → 두 설문 제출 → 포인트 시뮬레이션 완료 → 사진 등록 화면 도달을 확인했다. 실제 지급을 검증한 것은 아니다.

### 회원혜택 분석·회원 신청·제휴사 처리 요청 (2026-11-25, 개발 연동 미구현)
- GA4와 어드민에서 섹션별 활성 체류시간, 화면·질문·필드별 이탈, 신청→약관→신청완료→제휴사별 설문→사진등록 전환을 집계한다. 백그라운드 시간은 제외하고 visibilitychange/pagehide 시 배치 전송하며 중복 이벤트를 식별한다. 입력값·이름·전화·이메일·사진·생년월일을 GA4로 전송하지 않는다. 현재 analytics.js는 dataLayer 이벤트 준비 상태이며 실제 GA4 측정ID/GTM 및 어드민 수집 API는 미연결이다.
- 신청 완료는 서버 저장 성공 후에만 표시한다. 로그인 회원ID와 신청ID를 연결하고 신청한 업체, 필요한 정보의 스냅샷, 약관ID·버전·동의시각, 설문·사진 제출 상태를 저장한다. 현재 config.js의 김시놀은 테스트 회원이며 실제 회원정보가 아니다.
- 어드민에 혜택 신청관리와 제휴사별 처리함을 추가한다. 온유상조에는 동의받은 실명·연락처·이메일·생년월일·성별 및 온유상조 설문만 제공하고 아웃핏코드에는 승인된 회원정보·키·몸무게·이메일·아웃핏코드 설문·사진만 제공한다. 최종 허용 필드는 각 제휴사 약관과 대조 확정. 브라우저에서 숨기는 수준이 아닌 API 응답 단계의 업체별 필터링 필요.
- 업체별 제휴코드를 어드민에서 발급·회수·재발급한다. 코드는 URL에 넣지 않고 로그인 입력에 사용한다. 해시 저장, 만료·시도횟수 제한·세션 발급·업체별 권한분리·접근 로그를 구현하고 운영 담당자 인증정책을 확정한다. 업체 간 신청ID 변경이나 파일 주소 추측으로 다른 업체·회원 데이터 접근이 불가해야 한다.
- 제휴사 전용 화면에서 해당 업체 신청건만 열람한다. 온유상조 가입증서 또는 아웃핏코드 결과물을 업로드·전달한 후 처리완료한다. 발송 채널(이메일/문자/앱)과 성공확인 정책은 확정 필요. 단순 프론트 상태 변경을 실제 발송으로 처리하지 않는다.
- 처리 상태는 신청ID+업체ID로 관리한다. 신청접수/사진대기/처리중/완료/보완필요 상태를 공통 저장소에서 조회하고 제휴사 처리완료 후 어드민 및 회원혜택 UI에 반영한다. 두 업체는 각각 독립 상태이며 한 업체의 완료로 다른 업체를 완료 처리하지 않는다. 서버 트랜잭션·감사로그·충돌 방지 및 재처리 정책 필요.
- 검수: 두 업체 신청→회원ID 연결→업체별 최소정보→코드 로그인→다른 업체 접근 차단→증서 업로드 및 발송 결과→완료 동기화→새로고침/재로그인 유지. 설문 500P 중복 지급 방지·실패 재시도·GA4 DebugView와 관리자 집계 일치도 확인.
- 이번 GitHub 배포에는 위 API·제휴사 처리함 기능은 포함되지 않는다. 현재 완성된 회원혜택 UI와 프로토타입 설문/사진 흐름을 배포하며 운영 적용 전 위 작업이 필요하다.
